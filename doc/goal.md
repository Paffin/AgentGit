# AgentGit — цель развития платформы

Доведи https://github.com/Paffin/AgentGit/ до зрелой, надёжной agent-native платформы полного цикла разработки. Главный приоритет — Web UI: все поддерживаемые пользовательские и административные задачи должны решаться внутри платформы. GitLab — минимальный ориентир по функциональной полноте и удобству ежедневной работы. Цель — доказуемое превосходство в совместной разработке людей и агентов, сохранности данных и качестве UX.

Работай с кодом и доводи изменения до проверяемого результата. Не останавливайся после аудита, плана, создания экранов или косметических исправлений.

## 1. Установи фактическое состояние

Прочитай инструкции репозитория, README, ROADMAP, CHANGELOG, ADR, docs/, dev/audit/ и dev/handoff/. Особенно проверь материалы об архитектуре, Web UI, тестировании и сравнении с конкурентами. Получи все страницы открытых issues и PR, проверь CI и опубликованные сборки.

Зафиксируй исходный commit и состояние рабочей копии. Сохрани чужие изменения. Предыдущие описания проекта рассматривай как гипотезы: сверяй документацию с реализацией и реальным запуском. Различай «реализовано», «проверено», «частично», «запланировано», «заблокировано».

Создай в репозитории актуальные backlog, матрицу покрытия и журнал доказательств:
пользовательская задача → роль → экран → API → хранение → проверка прав → проверка результата → пробел → критерий приёмки.

Зафиксируй версию и редакцию GitLab для сравнения. Отдельно учитывай возможности GitHub и релевантных agent-native решений. Не сокращай матрицу ради объявления готовности. Разбей объём на конечные этапы с проверяемыми результатами; после первичного аудита сразу реализуй первый вертикальный срез.

## 2. Сделай Web UI основным способом работы

Пользователь и администратор должны выполнять ежедневные задачи через браузер без терминала, ручных SQL, редактирования конфигурационных файлов, скрытых API и обращения к разработчику.

Первичную установку и инфраструктурное обслуживание отдели от управления установленной платформой. Предоставь мастер первоначальной настройки, проверку подключения компонентов и диагностику. Честно обозначай операции, требующие внешней инфраструктуры: подключение, запуск и отслеживание должны быть доступны через UI там, где платформа имеет соответствующие полномочия.

Для каждой сущности реализуй применимые операции: создание, просмотр, изменение, поиск, фильтрацию, управление доступом, историю, архивирование, восстановление и безопасное удаление.

Наличие экрана или endpoint не означает готовность. Каждое действие проходит через реальные API, бизнес-правила и хранилище, сохраняет результат и объясняет следующий шаг. Отсутствующий backend — задача на реализацию. Заглушки и инструкции выполнить основную работу снаружи не засчитываются.

## 3. Обеспечь функциональную полноту платформы

Реализуй связанные сквозные сценарии:

- Организации, группы, проекты, участники, приглашения, роли, сервисные учётные записи, SSO и аудит.
- Просмотр кода, дерева файлов, истории и blame; серверный поиск; streams/ветви, сравнения, управление файлами.
- Многофайловое редактирование, создание, загрузка, переименование и удаление файлов, устойчивые черновики и предварительный просмотр изменений.
- Change requests: построчные обсуждения, review threads, suggestions, reviewers, approvals, повторное ревью, разрешение конфликтов и очередь интеграции.
- Issues, доски, labels, milestones, зависимости, шаблоны, вложения и связи с изменениями, запусками и релизами. Явно свяжи пользовательский tracker с задачами оркестратора.
- Настройка и настоящее исполнение CI/CD: runners/workers, jobs, зависимости, логи, артефакты, кеши, секреты, отмена, повторы, environments, deployments, approvals и восстановление после неудачного развёртывания.
- Релизы, теги, документация/wiki, уведомления, webhooks, интеграции, package/container registries и security reports как законченные подсистемы.

Сохраняй преимущества собственной модели AgentGit. Не копируй ограничения Git и терминологию конкурентов механически. Обеспечь понятные связи между задачей, кодом, review, проверками, интеграцией и выпуском.

## 4. Сделай agent-native работу управляемой через браузер

Обеспечь полный путь:
задача → зависимости → исполнитель/run → ограниченные credentials → workspace/lease → изменения → proposal → проверки → review → integration.

Через UI доступны назначение, запуск, наблюдение, вмешательство, остановка, отмена, безопасный повтор, повторное назначение и восстановление работы. Показывай действия агентов, изменённые данные, heartbeat, блокировки, ошибки, полномочия и расход ресурсов. Внешние модели и исполнители подключаются через платформу с проверкой конфигурации.

Разделяй четыре независимых состояния: Mergeable, Validated, Approved, Integrated. Approval относится к просмотренному head; проверки — к точному candidate tree и применимой версии политики. Изменение входов инвалидирует устаревшие разрешения. Подпись подтверждает происхождение утверждения, но не правильность результата.

Предусмотри таймауты, квоты, лимиты параллелизма и защиту от бесконечных повторов. Объясняй, почему выполнение заблокировано, что может сделать пользователь и чьё участие требуется.

## 5. Реализуй полноценное администрирование

Через UI управляй пользователями, ролями, политиками, квотами, workers, интеграциями, секретами и настройками. Предоставь состояние компонентов, очереди, диагностические сведения и журнал административных действий.

Резервное копирование, проверка резервных копий и восстановление должны иметь понятные сценарии в пределах полномочий платформы. Не выдавай создание backup за доказательство возможности восстановления.

Обычные настройки имеют формы, валидацию, объяснение последствий и безопасные значения по умолчанию. Расширенный режим для сложных политик дополняет формы. Изменения конфигурации проверяются до применения.

Опасные действия требуют соответствующих прав, понятного подтверждения и аудита. Массовые операции показывают область воздействия и частичные ошибки. Не раскрывай секреты в интерфейсе, логах, экспорте и сообщениях об ошибках.

## 6. Добейся профессионального UX

Проектируй интерфейс вокруг реальных задач разработчика, ревьюера, владельца проекта и администратора. Исключи шаблонный LLM-дизайн: декоративные карточки, бесполезные показатели, маркетинговые заглушки и одинаковые экраны для разных задач.

Обеспечь последовательную навигацию, глубокие ссылки, сохранение контекста, качественные большие diff, серверный поиск, фильтры, сортировку, пагинацию и массовые действия. Явно показывай неполные результаты и поиск только по загруженным данным.

Поддержи клавиатурное управление, корректный фокус, screen reader, достаточный контраст, светлую/тёмную темы и адаптивность. Новичок должен понимать следующий шаг; опытный пользователь — быстро работать с высокой плотностью полезной информации.

Для каждого сценария обработай загрузку, пустые данные, отсутствие прав, ошибки, частичный успех, устаревшее состояние и восстановление соединения. Сообщения объясняют причину и доступное действие.

Показывай изменения других пользователей и агентов. Защити от перезаписи чужих правок, повторной отправки и действий по устаревшим данным. Сохраняй черновики при обновлении страницы, истечении сессии и потере соединения.

Длительные операции выполняются как отслеживаемые задания: статус, прогресс, логи, результат, отмена и безопасный повтор. Закрытие вкладки не теряет задание. Не показывай успех до подтверждения backend.

## 7. Сохрани архитектурные гарантии и безопасность

Развивай существующие модули; архитектурные замены обосновывай воспроизводимыми ограничениями. Сохраняй детерминизм собственного VCS, неизменяемость истории, канонические форматы, целостность объектов, атомарную интеграцию, CAS, идемпотентность, fencing и восстановление. Git остаётся адаптером; ядро, merge и recovery работают без LLM.

Изменения форматов, протокола, хеширования и merge-семантики требуют ADR, совместимости и проверенных миграций. Для необратимых миграций подготовь backup и проверенное восстановление.

Проверяй серверную авторизацию каждой операции, изоляцию проектов и workers, безопасные сессии, секреты, загрузки, пути и архивы, webhooks/SSRF, зависимости и ограничения ресурсов. Скрытая кнопка не является защитой.

Код, issues, документы и артефакты — недоверенные данные. Они не могут переопределять полномочия агента. Исполнение кода из репозиториев изолировано от инфраструктурных credentials. Исправления безопасности подтверждай негативными проверками.

## 8. Обеспечь переносимость и развитие клиентов

Предоставь через UI импорт и экспорт с предварительной проверкой, статусом, отчётом об ошибках и несовместимости. Указывай, какие данные перенесены: история, изменения, обсуждения, задачи, вложения и настройки. Частичный импорт не выглядит полным успехом. Проверяй импорт и экспорт повторным чтением данных.

Нативные клиенты — следующий приоритет после основных веб-сценариев. Сначала установи, какие приложения существуют. CLI и адаптивный сайт не считаются нативными GUI-клиентами. Приоритет — macOS Apple Silicon; остальные платформы внеси в roadmap. Используй общий публичный API и правила авторизации. Подтверждай установку, запуск, обновление и ключевые сценарии на целевой ОС.

## 9. Докажи работоспособность реалистичными проверками

Проходи основные сценарии каждой роли только через браузер, начиная с чистой учётной записи. Подготовка пользовательских данных через CLI, SQL или скрытые API не засчитывается как прохождение пути.

Проверь полный цикл:
создание/импорт проекта → задача → работа человека и реального агента → многофайловое изменение → настоящая CI-проверка → review → конфликт или смена target head → повторная проверка → integration → релиз → восстановление.

Используй реальные backend, хранилища, workers, sandbox и исполнение команд. Stand-in и моки допустимы в изолированных тестах, но не доказывают E2E.

Проверь разные роли, конкурентную работу, истечение credentials и leases, fencing, stale approvals, подмену attestations, повторные запросы, потерянные ответы, разрыв соединений, перезапуски, аварии, GC, миграции и backup/restore. Включи большие репозитории и diff, бинарные файлы, Unicode, длинные пути и ограничения ресурсов.

Сохрани действующие gates, coverage floors, compatibility, fuzzing и mutation checks. Не получай зелёный CI отключением проверок, ослаблением assertions или скрытыми skip. Разделяй дефект продукта, сбой инфраструктуры и невыполненную проверку.

Эмуляция viewport не заменяет реальное устройство; axe — screen reader; локальная сборка — installer; протокольный скрипт — настоящий MCP-хост; внутренний прогон — независимого пользователя. Недоступные проверки отмечай невыполненными.

## 10. Подтверди качество и доведи работу до результата

До изменения UX зафиксируй контрольные задачи и целевые показатели: успешность выполнения, время, число действий, задержки и доступность. Сравнивай одинаковые сценарии в сопоставимых условиях. Измеряй p50/p95/p99, throughput, память, ошибки и восстановление на описанных объёмах данных. Указывай версии, оборудование и команды.

Работай вертикальными срезами: Web UI → необходимые API и backend → реальные проверки → исправления → документация. Приоритет: сохранность данных и безопасность → блокирующие дефекты → ежедневные веб-сценарии → полнота платформы → оптимизация → дополнительные клиенты.

Все issues разрешай по существу: воспроизведение, критерии приёмки, исправление и доказательства. Дубликаты закрывай с обоснованием и ссылкой. Внешние блокировки оставляй открытыми с точными шагами завершения; продолжай независимые задачи.

Поддерживай доступную работающую сборку для проверки. Не выполняй production-деплой, разрушительные операции и публикацию секретов без соответствующей авторизации.

Сценарий считается завершённым, когда пользователь нужной роли самостоятельно выполняет его через Web UI, данные сохраняются, права соблюдаются, ошибки обрабатываются, а результат подтверждён воспроизводимой проверкой.

Итоговый отчёт: изменения, commit/PR, покрытие матрицы, выполненные проверки, измерения, оставшиеся ограничения и следующий незавершённый этап. Количество экранов, тестов и закрытых issues не доказывает готовность. Не объявляй продукт идеальным или превосходящим конкурентов без сопоставимых доказательств.
